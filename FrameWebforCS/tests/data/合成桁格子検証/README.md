# 合成桁の設計例で橋面荷重を検証する

`合成桁の設計例と解説.pdf`（このフォルダ）の 36〜40 頁（本文の頁番号 24〜28。5.1 設計方針〜5.4.1 断面力）に示された格子解析を、FEMPython の橋面荷重（`bridge_loads`）で解き直し、結果を比べた記録です（2026-10-30、engineVersion 1.0.0+da2d03d）。

## 結論

- **荷重の配分は設計例と一致しました。** 橋面荷重の合計は全ケースで手計算と同じです（合成前 2824.2 kN、合成後 522.2 kN）。G1 の結果から逆算した合成後の線荷重 7.214 kN/m は、てこの原理の 7.218 kN/m とも、設計例の値から同じ方法で逆算した 7.22 kN/m とも合います。
- **断面力はおおむね ±1% で合いました。** ずれが大きいのは合成後死荷重の曲げモーメント Mvd で、G1 は小さく G2 は大きく、±3〜5% です。原因は荷重ではなく格子の剛性の仮定です（後述）。
- **FEMPython の側で直すべき問題が見つかり、直しました。** 橋面荷重の準備が三角形の数の2乗で遅く、細かいモデルは runner の 10 分の上限を超えていました。直した後は、0.25 m 間隔の 12 ケースが runner で 141 秒です（後述）。

### 設計例の値から分かること

- **Mv は合成後死荷重を含みます。** Mv＝Mvd＋ML です（例：G1 中央 3981＝500＋3481、本文 39 頁の ML）。
- **床版の荷重は、てこの原理で主桁に配っています。** 主桁の間は単純梁、張出しは G1–G2 の単純梁の張出しとして配ります。
  - 合成前死荷重の合計 85.57 kN/m と合成後死荷重の合計 15.825 kN/m は、Ms・Mvd の総和から逆算した値と一致します。
  - G1 の合成後の線荷重は、てこの原理で 7.218 kN/m です。設計例の Mvd（J1 542、中央 500）から「線荷重＋中央の集中力」として逆算した 7.22 kN/m と合います。

- **横分配影響線（本文 100 頁）は、主桁の間で直線です。** 主桁の位置の値は G1 0.731、G2 0.367、G3 0.072、G4 −0.170 です。

### 張出しの荷重をてこの原理で配る方法

橋面荷重は、構造の節点が囲む範囲の外へ荷重を載せられません（外挿は拒否）。張出しの荷重を設計例と同じ「G1–G2 の単純梁の張出し」として配るため、次の部材を足しました。

- 床版の端（y＝−1.025、8.675）の各断面に節点を置き、片持ちの部材（要素 7）で G1・G4 に剛結する。
- G1→G2・G4→G3 に伝達の部材（要素 6）を置き、G2・G3 側の端の回転をすべて解放する。

主桁のねじり剛性がほぼ 0 なので、G1 の回転を止めているのはこの伝達の部材だけです。そのため張出しの荷重による偶力は、G1 に＋Pe/s、G2 に −Pe/s として伝わります。G1 と G2 のたわみの差では力は生じず、伝達の部材は格子の剛性を足しません。

### 荷重（すべて橋面荷重。普通の部材荷重は使わない）

- **パネル**：床版の全幅（6 本の線 × 断面）を三角形で覆うパネルを1つ作る。
- **面荷重**：橋軸方向の2本の経路のあいだに載せる。
- **線荷重**：1本の経路に載せる。ハンチ・鋼重は主桁の線の上に置く。

| ケース | 内容 | 断面 |
|---|---|---|
| 1 | 合成前死荷重 Db | 鋼桁 |
| 2 | 合成後死荷重 Da | 合成 |
| 3〜6 | 横分配の確認：支間中央の G1〜G4 に 100 kN の節点荷重 | 合成 |
| 7〜12 | 活荷重（`scripts/live.json`） | 合成 |

活荷重は、最も不利な位置を自動では探せないので、位置を次のように決めて載せました。設計例に載荷位置は書かれていないため、これは仮定です。

- **強度**：p2（3.5×1.241 kN/m²）は全支間に載せる。p1（曲げは 10、せん断は 12 kN/m²、×1.241）は長さ 10 m。
- **幅**：主載荷 5.5 m は地覆の内側の左端（y＝−0.425）から全強度。その外は 1/2 の強度を、影響値が正の範囲だけに載せる。G1 は y＝5.844（G1 の横分配が 0 になる位置）まで、G2 は y＝8.075 まで。G2 の反力だけは主載荷を y＝−0.2〜5.3 とした。
- **p1 の橋軸方向の位置**：支間中央の曲げは x＝11.5〜21.5、J1 の曲げは x＝7.144〜17.144（両端の影響値が等しくなる位置）、反力は x＝0〜10。

### 設計例との差を調べたこと（2026-10-30。どちらも原因は未確認）

モデルは変えていません。設計例の値も変えていません。下の変種は感度を見るためだけのもので、結果の表には使っていません。

**合成前死荷重のたわみ（設計例 93 mm、こちら 87.6 mm）**

- 設計例（本文 104 頁）の内訳は、支間中央で δ1（鋼重）19 mm、δ2（床版・ハンチ・型枠）74 mm で、G1・G4 と G2・G3 が同じ値です。設計例は「格子解析結果より」と書いています。
- こちら（0.25 m 間隔、せん断変形なし）は G1 87.61 mm、G2 87.71 mm です。
- 格子とは別に、単純梁の単位荷重法で計算しました。断面二次モーメントは設計例の鋼桁の値（Sec-1・Sec-2 の段付き）、荷重は設計例の Ms から逆算した等分布（G1 22.10 kN/m、G2 20.69 kN/m）です。結果は G1 88.2 mm（δ1 17.6＋δ2 70.6）、G2 87.1 mm（δ1 18.6＋δ2 68.5）で、こちらの格子と合います。
- したがって、設計例と同じ断面二次モーメントと曲げモーメントから、曲げ変形だけで出るたわみは約 88 mm です。設計例の 93 mm（約 6% 大きい）には、本文に書かれていない仮定が入っていると考えます。せん断変形（主桁に入れると 90 mm）だけでは届きません。荷重や断面のどの扱いかは確かめられていません。

**合成後死荷重の Mvd と横桁の力（設計例の横桁のせん断力 58.6 kN、こちら 61.5 kN）**

- 設計例の横桁の死荷重の断面力（本文 108 頁）は Sd＝51.2 kN、G2 の位置で Md＝−130.7 kN·m（＝51.2×2.55。G1 側はピン）です。こちらの合成前と合成後の和は 55.4 kN です。
- 感度を見るため、2.75 m 間隔のモデルで、横桁の断面二次モーメントだけを 0.7 倍にした変種を解きました（スクリプトはリポジトリに入れていません）。

## 見つかった問題

1. **橋面荷重の準備が、三角形の数の2乗で遅かった（直しました、2026-10-30）**
   - **症状**：runner は三角形 140 個（2.75 m 間隔）・12 ケースで 25 秒でした。360 個（1.0 m 間隔）では 10 分の上限を超えて `CANCELED`（`results/runner_1.0m_canceled.json`）になり、1,320 個（0.25 m 間隔）も同じでした。
   - **原因1**（`FrameWeb/src/fem/spatial_loads/validation.py` の `prepare_panel` と `prepare_geometry`）：載荷メッシュ（`loading_nodes`）が無いとき、`prepare_panel` は `domain_cells = cells` としていました。そのため `for cell in panel.cells: for domain in panel.domain_cells or panel.cells:` が、面荷重の帯ごとにセルを総当たりで切り抜いていました。三角形 140 個の面荷重2つで `clip_polygon` が 78,400 回です。
   - **原因2**（`FrameWeb/src/fem/spatial_loads/geometry.py` の `validate_partition`）：セルが重ならないことの検査が、全部の組を `clip_polygon` で切り抜いていました。三角形 1,320 個で約 87 万回です。
   - **直し方1**：載荷メッシュが無いときは `domain_cells` を空（＝構造のセルが載荷範囲）のままにしました。面荷重の切り抜きは、空なら当のセルだけで切ります。検査済みのセルは重ならないので、ほかの組の面積は 0 です。
   - **直し方2**：`bounding_box_pairs` を足しました。x の順に並べて掃引し、外接矩形が両方の軸で正の幅で重なる組だけを切り抜きます。外接矩形が離れているか接するだけの組は、重なりの面積が 0 なので省けます。
   - **回帰テスト**（`FrameWeb/tests/spatial_loads/test_geometry.py`）：
     - 帯状のグリッド（三角形 80 個）で、`prepare_geometry` と `prepare_panel` の `clip_polygon` の回数がセル数の 5 倍未満であること。直す前は 12,842 回と 3,160 回で失敗しました。
     - 全面の面荷重で、各セルに一度だけそのセルの面積が配られること。
     - `bounding_box_pairs` が、接する場合を含む乱数のセルで総当たりと同じ組を返すこと。
   - **効果**：0.25 m 間隔の 12 ケースが、FemModel を直接動かして 145 秒（`results/time_0.25m_none_after_fix.log`）、runner で 141 秒（`results/runner_0.25m_after_fix.json`）になりました。結果は直す前と同じです（最大差 0）。
     - 直す前の記録 `results/time_0.25m_{none,cross}.log`（面荷重のケースが 1 ケース 60〜85 秒）は、原因1だけを検証のスクリプトの中で差し替えて測ったものです。
     - 直した後も、面荷重のケースは 1 ケース 16〜21 秒かかりました。内訳は積分とパネルの準備です。
   - **2回目の直し（2026-10-30）**：残りの時間を cProfile で分け、次の3つを直しました。
     - **積分の点ごとの検査のやり直し**（約半分）：`shape_values`・`natural_coordinates`・`StripCell.intensity` が、積分の点ごとにセルや帯の凸性の検査（`validate_polygon`）をやり直していました。準備のときに同じ条件で検査済みなので、`assembler.py` からは `validated=True` で呼び、検査を省きます。外挿を拒む `contains_point` は点ごとに残しています。
     - **外周の三角形分割**（約2割）：`triangulate_simple` が、同じ直線上の頂点（床版の端の各断面）を、耳を探すたびに全頂点と照らしていて、頂点数の2乗でした。先に同一直線上の頂点を1回の走査で除きます（耳の切り取りでも三角形を作らずに除いていた頂点なので、面積は同じです）。外周と穴の分割は、面荷重ごとではなくパネルごとに1回だけ作ります。
     - **外周の自己交差の検査**（約1割）：`validate_polygon` が辺の全部の組を調べていました。外接矩形を許容差 eps だけ広げ、2 eps 以内に近づく組だけを調べます（`_nearby_edge_pairs`）。`segments_intersect` が交わると見るのは、辺から eps・端から eps の範囲（各軸で eps×√2 以内）なので、それより離れた組は交わりません。
     - **回帰テスト**：`compile_spatial_loads` の `validate_polygon` の回数がセル数の 5 倍未満（直す前は 1,564 回で失敗）、長い長方形の外周で `triangulate_simple` の `contains_point` の回数が頂点数の 10 倍未満（直す前は 20,301 回で失敗）で、三角形の面積の和が長方形の面積と同じこと、`validate_polygon` の `segments_intersect` の回数が頂点数の 10 倍未満（直す前は 20,502 回で失敗）。あわせて、隣り合わない辺が許容差の内（eps/2）で接する輪を引き続き拒むこと、乱数の輪で総当たりと拒否の結果が同じことを確かめます。
     - **効果**：0.25 m 間隔の 12 ケースが FemModel を直接動かして 66 秒（`results/time_0.25m_none_after_fix2.log`。面荷重のケースは 1 ケース 7〜8 秒）。結果は1回目の直しの後と同じです（数値 243,874 個で最大差 0）。
     - **残り**：積分の点ごとの計算（帯の Q4 の逆写像の Newton と `contains_point`）が面荷重のケースの半分ほどを占めます。点の数に比例する重さで、2乗ではありません。ほかに、節点の重なりの検査（`prepare_panel`）が節点数の2乗、積分の値のベクトルが「断片 × パネルの全節点」の密な配列で、もっと大きいパネルでは2乗で効きます。凹んだ外周（同一直線上でない頂点が多い）では `triangulate_simple` は今も頂点数の2乗です。どれも今回は直していません。
2. **張出しには作り込みが要る**：橋面荷重は構造の外へ載せられないので、上の「張出しの荷重をてこの原理で配る方法」が必要でした。
3. **3D の runner は PIK を止める必要がある**：`--generate-pik false` が要ります（既定のままだと `PIK_REQUIRES_2D`）。

## デスクトップで目で確かめる

`合成桁格子_橋面荷重検証.json` を FrameWebforCS で開きます。

- **中身**：節点 2.75 m 間隔、せん断変形なしのモデル（`models/model_2.75m_none.json`）に、ケース名・記号と組合せを付けたもの。`scripts/make-visual.mjs` で作りました。
- **計算時間**：12 ケースで 30 秒ほどです。

- デスクトップの読込（`InputDataService.JsonDataOpen`）→ 保存（`GetSaveJson`）を通しても、節点・部材・結合・支点・荷重・組合せ・橋面荷重（パネル 1、三角形 140、経路 33、ケース別の荷重 41）の数は変わりません。計算要求（`CalculationRequestBuilder.FromSavedJson`）も作れました。

## 作り直し方

リポジトリの直下（`FEMPython`）で、PowerShell から実行します。

```powershell
$d = "FrameWebforCS/tests/data/合成桁格子検証"
# runner（2.75 m 間隔）
$env:SHEAR = "none"; $env:DX = "2.75"; $env:LIVE_SPEC = Get-Content "$d/scripts/live.json" -Raw
node "$d/scripts/gen.mjs" "$d/models/model_2.75m_none.json"
New-Item -ItemType Directory C:\tmp\grid-run
& FrameWebforCS/Headless/bin/Release/net10.0-windows/FrameWebforCS.Headless.exe run `
  --input (Resolve-Path "$d/models/model_2.75m_none.json") --output-dir C:\tmp\grid-run `
  --generate-pik false --generate-pdf false
node "$d/scripts/read.mjs" C:\tmp\grid-run\result.json "$d/models/model_2.75m_none.map.json"

# FemModel を直接（0.25 m 間隔。runner でも解ける）
New-Item -ItemType Directory C:\tmp\grid-fine
$cases = foreach ($c in 1..12) {
  node "$d/scripts/onecase.mjs" "$d/models/model_0.25m_none.json" $c "C:\tmp\grid-fine\m_case$c.json"
  "C:\tmp\grid-fine\m_case$c.json"
}
uv run --project FrameWeb --locked python "$d/scripts/drive.py" C:\tmp\grid-fine\result.json @cases
node "$d/scripts/read.mjs" C:\tmp\grid-fine\result.json "$d/models/model_0.25m_none.map.json"
```
