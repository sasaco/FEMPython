# Desktop print parity inventory

## Reachable legacy controls and desktop contract

`print.component.html` exposes checkboxes 0–9 and 11–15. IDs 10 (PrintScreen) and 16 (reaction diagram) occur only inside commented HTML and are not reachable; `print.service.ts:110-140` retains their option IDs. The desktop `PrintOption` enum reserves these IDs and rejects them. The table/result checkboxes require a calculated result (`print.component.html:58-195`); diagrams 11–14 have the same guard (`:257-318`), while load diagram 15 is available with input only (`:239`).

The parser builds all input and result readers from root dictionaries, and activates result pages by `*Name` keys (`FramePrintPDF/PDF_Manager/PrintData.cs:42-113`; `PrintInput.cs:95-155`). `InputDataService.GetSaveJson()` places saved results inside `result` (`InputDataService.cs:396-407`), so passing it directly loses result reports. `PrintProjection.Build` writes selected canonical and derived rows at the root. It intentionally throws on absent selected data.

## Filters, layout, output

Legacy custom displacement, reaction, and section-force editors expose axis maxima and minima (`print-custom-disg.component.html:13-149`, `print-custom-reac.component.html:13-149`, `print-custom-fsec.component.html:17-87`). The section-force editor also filters members (`print-custom-fsec.service.ts:10-71`); the print service applies these filters in `dataChoiceFsec` and `dataChoice` (`print.service.ts:583-720`). Static, COMBINE, and PICKUP choices share the editor for each family. The old multi-selection code forces all axes (`print.service.ts:587-602,710-712`); the desktop selection keeps each family filter independent across simultaneous choices. `DisplacementComponents`, `ReactionComponents`, and `SectionForceComponents` accept their respective maxima/minima; `DiagramComponents` controls result screenshots/vector diagrams; `LoadDiagramComponents` controls 2D axis/load output. Null selects all within that family, and the original `Components` remains a fallback. Unknown components and missing selected rows fail explicitly. Component, node, and member ID filters are validated.

The diagram editor exposes result components 0–6, split horizontal, split vertical, single layout, portrait/landscape, and X/Y scales (`print-custom-three.component.html:11-160`). Legacy JSON uses `layout`, `output`, reciprocal `scaleX`/`scaleY`, and `pageOrientation` (`print.component.ts:225-279,879-946`). Desktop `PrintSelection` carries these choices. `PrintData` accepts `pageSize` A3/A4 and language/title (`PrintData.cs:37-65`); desktop offers both paper sizes, though the old print UI does not present a paper-size control. Browser printing uses `printJS` on the preview's Base64 PDF (`print.component.ts:1045-1048`). Desktop sends exactly the generated preview bytes to a printer.

`PrintScreenData` is an array of `{ mode, title1, result[] }`, each result holding PNG `src`, `title`, `type`, maximum/minimum, and displacement subinformation (`FramePrintPDF/PDF_Manager/Printing/Diagram3D/ResultLoadDiagram.cs:10-49`). The 3D projection requires a captured PNG for every ordered `PrintDiagramRequest` and maps images to this root key. The viewport agent owns occlusion-independent capture. For 2D, `diagramInput` and `diagramResult` are the legacy vector path; they do not add redundant screenshots. The 3D section request list retains all six force components. The 3D load request list has one combined axis/load capture per named load case, matching `three.service.ts:getCaptureImage`.

The base 2D `PrintDiagram.diagramResult.output` includes `disg` after `mz`, `fy`, and `fx`, matching the legacy append order (`print.component.ts:910-934`). `PrintDiagram.disg` and `disgName` are attached only when `disg` is selected. COMBINE/PICKUP vector diagrams retain their three force components. For a mixed static/modal result set, each base report and 3D capture uses only cases with rows in that family; displacement can include modal pages while reaction and section force use applicable force-analysis pages. Explicit unknown case IDs and selections with no eligible rows still fail.

## Fixtures and known gaps

Focused `PrintProjectionTests` construct input-only, static, nonlinear, modal, moving-parent/child, mixed-family, and derived snapshots directly and compare root keys and row values. The isolated project `FrameWebforCS/tests/PrintProjection.Tests/PrintProjection.Tests.csproj` links those tests because the existing aggregate test project currently has unrelated `LoadDisplayConversionTests` compilation errors. The tests invoke `DirectPdfGenerator` for input-only, static reports, and moving envelopes; each returned PDF has a valid PDF signature. PDF import checks A4 portrait and A3 landscape page geometry. Simultaneous displacement/reaction/section choices, independent 2D load/result diagram filters, `disg` alone and with force outputs, mixed default/explicit cases, and invalid family components are covered. Missing or unselected result cases, empty derived data, stale revisions, missing image captures, invalid scales, and unknown options are explicit errors.

Current C# canonical output has static, nonlinear load-step, and modal shapes (`CalculationResultModels.cs:366-445`); `PrintProjection` can print modal displacement but reactions and member forces have no modal source and are rejected when chosen for modal-only cases. `PrintProjection.GetAvailability()` lets the modal explain/disable those options. The legacy HTML has no separate shell/solid result print option (`print.component.html:45-195`), so these are outside the reachable print inventory even though canonical results may contain them. Moving-load parent and children are now projected as legacy `*_max`/`*_min` dictionaries with source-case provenance (verified by a three-case LL fixture and direct PDF generation). Derived section-force station positions come from canonical topology; an unknown station fails explicitly. Rendered-page image comparison and interactive GL/printer operation remain end-to-end sign-off gates owned by the integrating team.
