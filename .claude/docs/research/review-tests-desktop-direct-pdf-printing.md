# Test Review: Desktop Direct PDF Printing

## Summary

Follow-up required before full legacy print parity can be signed off. The focused suites exercise direct invocation, representative projection data, an input-only modal preview, and real off-screen GL capture. They do not yet prove the product printer path or compare rendered legacy and desktop reports. Coverage was not measured, and no percentage is inferred.

## Review Scope

Reviewed `AGENTS.md`, the approved `desktop-direct-pdf-printing.md` plan, the print parity inventory, `.agents/logs/review-diff-desktop-direct-pdf-printing.patch`, all new focused print tests and smoke harnesses, and their relevant production call sites. The unrelated `partial-member-spring-intervals.md` file was excluded. This reviewer did not edit product code or rerun the test suites; the integrating lead reports focused suites of 7, 15, 9, and 5 passing tests. The aggregate solution remains blocked by 12 pre-existing `LoadDisplayConversionTests.cs` CS0103 errors.

## Findings

- [High / P1] `FramePrintPDF/PDF_Manager.Tests/PrintLibraryWebView2Tests.cs:48` and `:50-52`; `FrameWebforCS/components/print/PrintDialogForm.cs:417-424` — The only printing probe writes a second PDF with `PrintToPdfAsync`, then intentionally selects a nonexistent printer and expects `PrinterUnavailable`. No test invokes the product's `ShowPrintUI(System)` path or verifies an actual virtual-printer spool job, selected page range, paper/orientation, copies, cancellation, or byte identity with the displayed document. Add a target-Windows STA smoke test that opens the product modal, prints the loaded multi-page PDF to a virtual printer through the same UI path, and independently checks output pages/settings against the displayed bytes. Keep a documented interactive run if the printer dialog cannot be automated reliably.
- [High / P1] `FrameWebforCS/tests/PrintProjectionTests.cs:44-52`, `:84-94`, `:120-152`; `FramePrintPDF/PDF_Manager.Tests/PrintLibraryTests.cs:17-25`, `:95-105` — The current PDF assertions establish a header, parseability, page count, and presence of an image object. They cannot detect omitted report rows, wrong case/component, broken CJK text, pagination, A3/A4 size, portrait/landscape, or horizontal/vertical multi-diagram composition. The approved plan requires semantic and rendered-page comparison for every reachable option. Check in representative expected contracts and independently parse text/page geometry; render approved legacy and desktop PDFs for input, static/nonlinear/modal/moving, DEFINE/COMBINE/PICKUP, long tables, Japanese text, filters, and each diagram layout. Assert actual page content and image placement, not merely `%PDF`.
- [Medium / P2] `FrameWebforCS/tests/PrintUi.Tests/PrintDialogFormTests.cs:109-156`; `FrameWebforCS/components/print/PrintDialogForm.cs:277-366` — The modal preview test generates once from input-only data and closes. It never seeds an existing preview and forces cancellation, stale document revision, projection/generation failure, failed WebView2 navigation, or close during background work. Those paths are responsible for preserving the prior preview and preventing late publication. Add STA tests with a prior displayed PDF and controlled failures at each boundary; assert displayed bytes, source URL, page controls, save/print enabled state, and temporary-file cleanup remain coherent.
- [Medium / P2] `FrameWebforCS/tests/PrintViewportSmoke/Program.cs:74-125`; `FrameWebforCS/tests/PrintViewportStateTests.cs:26-119` — The real GL smoke captures one displacement mode; service tests change modes but do not compare captured PNGs. There is no rendered proof for load, six section-force components, COMBINE/PICKUP, both dimensions, selected case ordering, or legend/scale values per mode. Add a mixed multi-request real-context fixture under the covering modal; inspect each PNG and its PDF placement, assert nonempty mode-specific model/annotation regions and stable order, then compare full UI state after success and after a later request fails.
- [Medium / P2] `FramePrintPDF/PDF_Manager.Tests/PrintLibraryTests.cs:40-55`; `FramePrintPDF/PDF_Manager/DirectPdfGenerator.cs:10-29` — Boundary tests cover oversized request text, malformed JSON, and cancellation before entry, but not the page, PDF byte, diagram image/pixel limits, generation while another caller holds the serialization lock, or cancellation during work. Add deterministic limit fixtures and concurrency/cancellation probes with bounded timeouts; verify failures retain the original exception and do not poison the next valid generation.
- [Medium / P2] `FrameWebforCS/tests/PrintUi.Tests/PrintDialogFormTests.cs:81-107`; `FrameWebforCS/AppComponent.cs:28-33`; `FrameWebforCS/components/menu/MenuComponent.cs:69-73` — Owner/modality is tested by constructing `PrintDialogForm` directly. The actual menu and `AppComponent.ShowPrintDialog` wiring, single-instance/reopen behavior, main-window focus restoration, and save-dialog write failure are not exercised. Add one actual-app STA menu command test with a timeout and close/reopen cycle, plus a save failure test that proves an existing destination remains unchanged and the modal can continue.

## Effective Existing Checks

- Direct generator tests parse a generated PDF, exercise repeated calls, reject malformed/oversized input, honor pre-cancellation, and embed a 3D PNG.
- Projection tests exercise stable reachable option IDs, root-level result placement, static/nonlinear/modal and moving data, derived provenance, filters, unavailable results, stale snapshots, invalid scales, and missing image captures.
- The real-context GL smoke verifies occlusion independence, model and annotation pixels, repeat capture, resize, partial-failure state restoration, and disposed-context rejection for a displacement fixture.
- Modal tests verify default controls, independent component lists, owner blocking, successful input-only WebView2 preview, and atomic replacement of exact supplied bytes.

## Validation Boundary

The green focused suites support those specific assertions. They do not establish full rendered report parity or printer operation. No product defect is inferred from the user-provided `AssertFailed` screenshot; the lead traced it to an earlier xUnit modal test assertion and reports that the corrected suite passes.
