## Implementation Plan: Desktop Direct PDF Printing

### Purpose
Add the complete legacy print workflow to the active `FrameWebforCS` client in an owner-bound modal popup, with selection, preview, PDF saving, and physical printer output. Generate PDFs by calling reusable `FramePrintPDF` code in process, without a print HTTP request.

### Scope
- New files: a `FrameWebforCS/components/print/` owner-bound modal selection, preview, and printer window; a focused `FrameWebforCS/providers/` print projection and invocation boundary; print contract, modal lifecycle, printer, and acceptance tests under `FrameWebforCS/tests/`; representative print fixtures and expected outputs under that test tree.
- Modified files: `FrameWebforCS/FrameWebforCS.csproj` for a direct `FramePrintPDF/PDF_Manager/PDF_Manager.csproj` reference and an embedded preview dependency if the feasibility gate passes; `FrameWebforCS/components/menu/MenuComponent.cs` for the existing print command; `FrameWebforCS/AppComponent.cs` only if needed to supply the modal owner or current state; `FrameWebforCS/three/ThreeComponent.cs` for live diagram capture. Change `FramePrintPDF/PDF_Manager/PrintInput.cs`, `PdfDocument.cs`, or `PDF_Manager.csproj` only where the direct byte API, runtime compatibility, bounded work, or dependency/font review proves necessary.
- Dependencies: the existing `PDF_Manager` print implementation, current `InputDataService` input state, `CalculationResultStore` canonical results, current 3D viewport, and an embedded PDF renderer that can preview and send the same PDF to a printer on the target Windows runtime. The present checkout has no typed `PDF_Manager.Printing` project; earlier design records describing it are not implementation evidence.
- Out of scope: changes to the FEM solver, calculation transport, `FrameWebforJS` behavior, `FrameGConverter`, a new print HTTP service, unrelated desktop UI changes, and preservation of `FramePrintAzure` call compatibility or buildability.

### Implementation Steps

Complete each gate in order; a failed compatibility or parity gate must be resolved before the following step begins.

#### Step 1: Prove the direct library and preview boundary
- [ ] Add a minimal direct-reference probe from the `net10.0-windows` client/test graph to `PDF_Manager` (`netcoreapp3.1`), generate a small PDF from a checked-in legacy fixture, and open its bytes in a `FrameWebforCS` owned modal preview window. Confirm that no print HTTP process is needed.
- [ ] Prove that the chosen in-app PDF renderer can print the previewed bytes through a Windows printer dialog with page range, paper/orientation, and copies, including cancellation and a virtual printer smoke test. If it cannot, choose a renderer/printing path that can before proceeding.
- [ ] Establish a Windows STA test host with a WinForms message pump for preview and print checks, plus an interactive OpenGL smoke path for Step 5. Prove the capture path can render while an owner-bound modal popup completely covers the viewport. Record which checks can run in CI and require a target-Windows interactive run for checks that cannot.
- [ ] Audit the actual package graph, embedded font redistribution, global font resolver, and `PrintInput` error behavior. Select and document the smallest safe print-library changes for the desktop. If the direct reference or preview/print path cannot run, resolve its target/framework or renderer dependency before proceeding; `FramePrintAzure` compatibility is not a constraint.
**Verification**: `dotnet build FrameWeb.sln` and a focused STA message-pump probe produce a parseable PDF, display it in the WinForms host, and spool the same PDF through an in-app print dialog to a virtual printer on the target runtime. The OpenGL smoke harness starts a real context and verifies capture with the modal over the viewport. A missing renderer runtime produces a clear local error; a direct build/runtime/print/capture failure blocks subsequent steps.

#### Step 2: Freeze the legacy print parity contract
- [ ] Inventory every reachable `FrameWebforJS/src/app/components/print/` selection, custom filter, orientation, paper, split layout, scale, input/result/derived report, and diagram option, recording the JSON keys consumed by `PrintData` and the source of each value in `FrameWebforCS`.
- [ ] Check in representative legacy print fixtures and current C# project/result fixtures, including missing results, static/nonlinear/modal and moving cases, DEFINE/COMBINE/PICKUP, long tables, Japanese text, and 3D diagrams. Mark any legacy option with no current C# data source as a blocking gap to resolve before parity sign-off.
**Verification**: a reviewed inventory maps each legacy control and output to a C# control/data source and a fixture; schema/fixture tests fail on missing or extra mapped options. Any unmapped option blocks completion rather than becoming an implicit exception.

#### Step 3: Build an atomic C# print projection
- [ ] Snapshot current input, selected case/results, derived definitions, print settings, and document/result revision on the UI thread. Convert them into the exact root legacy dictionaries expected by `PrintInput`, rather than passing `InputDataService.GetSaveJson()` with its nested `result` field.
- [ ] Validate selections and numeric/layout bounds before invoking the PDF library. Reject unavailable/stale results, invalid case/filter references, unsupported diagram combinations, and document changes during asynchronous preparation without overwriting a newer preview.
- [ ] Add deterministic tests for input-only output, all result families and derived output, stable order/names, missing/invalid data, and stale generation cancellation.
**Verification**: projection tests compare the generated print data with checked-in expected contracts and generate parseable PDFs for representative cases; invalid or stale snapshots produce no PDF and leave the prior preview intact.

#### Step 4: Expose one bounded direct PDF generation path
- [ ] Add a byte-producing `PDF_Manager` API or a narrow adapter over its existing public API. Use one immutable request and one generated byte array for preview, save, and printer output; avoid HTTP and repeated Base64/JSON round trips within `FrameWebforCS`.
- [ ] Define size/page/image/time limits and serialized access around mutable PDF/font state. Preserve exception context, surface user-safe errors, and release partially created documents and buffers on cancellation or failure.
**Verification**: direct invocation tests assert valid PDF structure, selected page count/text/layout, semantically repeatable output (allowing clock metadata), bounded rejection, and preview/save/print source byte identity. The desktop and `PDF_Manager` project build; Azure caller compatibility is not tested.

#### Step 5: Capture every selected diagram before building the print UI
- [ ] For each chosen load, force, displacement, COMBINE, or PICKUP diagram, switch the existing `ThreeComponent` to the corresponding mode/result, render and capture it on the WinForms UI thread, and store it with the legacy title/mode/result/order expected by `PDF_Manager` for single/horizontal/vertical layouts.
- [ ] Capture a composite of the GL scene, text labels, legends, and other visible WinForms overlays without reading occluded desktop/window pixels. Render the scene through an off-screen GL target or another verified occlusion-independent path, and draw labels/legends into the output bitmap from the same presentation state; refactor the existing HWND-only label/legend drawing path as needed. Restore the original mode, case, camera, selection, and visible state after success, cancellation, or failure.
- [ ] Bound capture count, dimensions, and image memory. Ensure hidden, empty, disposed, or unavailable OpenGL contexts fail clearly without creating a second renderer or freezing the UI.
**Verification**: multi-diagram tests and rendered-page fixtures check stable order, mode-specific nonempty images, layout, orientation, scales, labels/legends, and exact UI-state restoration after partial failure; the real-context interactive smoke gate covers repeated capture with the modal fully covering the viewport, resize, close, and unavailable context on the target Windows machine. The PDF image must exclude modal controls while retaining the model and its labels/legend.

#### Step 6: Add the complete modal print workflow inside `FrameWebforCS`
- [ ] Wire the existing print menu to open one owner-bound modal window with `ShowDialog(owner)`. Reproduce every inventoried legacy control, default, conditional visibility, result filter, diagram option, and page navigation action in that popup; closing or cancelling returns focus to the unchanged main window.
- [ ] Render the generated PDF in the embedded preview control and save exactly those bytes through a WinForms save dialog with atomic replacement. Send that same PDF to the selected physical/virtual printer through an in-app print dialog with supported page-range, paper/orientation, and copies controls. Handle cancel, generation failure, write failure, printer/spooler failure, close/disposal, and missing renderer runtime without corrupting current document or prior preview state.
**Verification**: STA message-pump UI tests cover menu open, owner and modality, blocked main-window interaction, every option and preview update, navigation, save/print/cancel/error states, print setting propagation, focus restoration, single-instance behavior, and reopen/dispose without leaked controls or temporary files. A target-Windows virtual-printer smoke test confirms the chosen pages and copies from the displayed PDF.

#### Step 7: Verify end-to-end parity and integration
- [ ] Compare legacy and C# generated PDFs for the complete Step 2 inventory using semantic assertions and rendered-page reviews, including pagination, A3/A4, portrait/landscape, CJK text, selected result cases, custom filters, and diagrams. Resolve every discrepancy; any proposed scope exception requires a separate user decision before sign-off.
- [ ] Run the focused C# tests, `dotnet test FrameWeb.sln`, `dotnet build FrameWeb.sln`, and the `PDF_Manager.csproj` build/tests relevant to any shared-library edit. Do not use the `FramePrintPDF.sln` build as a gate because it includes the out-of-scope `FramePrintAzure` project. Check the app with no print host running, and inspect the final diff for unrelated changes.
**Verification**: every legacy scenario passes automated contract/PDF checks plus target-Windows interactive modal preview/save/virtual-printer smoke runs where a headless CI run cannot provide a real printer or GL context; the desktop and directly used print project build, relevant tests pass, and no print POST is issued by `FrameWebforCS`. An unavailable interactive environment leaves parity unverified, not waived.

### Risks & Considerations
- The actual `PDF_Manager` is an old `netcoreapp3.1` project with `PdfSharpCore` and embedded fonts; direct `net10` compatibility, font rights, and package advisories require Step 1 evidence before adopting it. Earlier typed-printing design documents describe files absent from this checkout.
- `InputDataService.GetSaveJson()` nests results under `result`, while the old print parser expects root `disg` and related dictionaries. A direct string pass would silently omit result reports; Step 3 establishes an explicit projection with fixture coverage.
- Existing `PrintInput` exposes a Base64 result, has mutable font state, and loses error provenance in a catch/rethrow path. Desktop invocation must be bounded and diagnosable. `FramePrintAzure` may no longer compile after print-library changes; it is outside the requested validation scope.
- The current OpenGL component has no capture API. Each legacy diagram mode needs its own UI-thread capture and full scene/label/legend composition even while the modal obscures the viewport, followed by state restoration; desktop pixel capture would include the popup or lose annotations.
- The PDF renderer is an additional Windows runtime/deployment dependency. Step 1 verifies preview and printing in a modal window on the target environment, and Step 6 handles absence and temporary-file cleanup if the control needs local PDF files.
- Existing `FramePrintPDF` has no automated test project. Add focused tests where the contracts live and use an independent PDF parser/rendered-page check for acceptance; a successful HTTP or PDF header check alone cannot prove parity.

### Open Questions
- None for product scope: the user confirmed full legacy print parity, including physical printing and PDF preview/save, in a `FrameWebforCS` owned modal window. `FramePrintAzure` compatibility/buildability is not required. Step 1 must make and verify the implementation choices for framework adaptation and the embedded PDF renderer/printer path before later steps start.
