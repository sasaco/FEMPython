## Implementation Plan: Partial Member Spring Intervals

### Purpose
Allow each member-spring case to define consecutive spring intervals measured from the member I end, while preserving whole-member behavior for existing rows with no length. Keep calculation, the grouped WinForms editor, the 3D view, and printed input consistent with the original member and its entered rows.

### Implementation status (2026-09-30)
The implementation is in the working tree. The shared row-operation API was completed first, then the spring editor, request projection, Python element splitting, 3D view, and PDF input and diagram changes. Each spring sheet displays the fixed 100,000 canonical rows. A sorted presentation places rows with the same member number together; two or more rows for one member form a Spread row outline, while a single row stays ordinary. Original `row` IDs remain stable for save, calculation, and viewport selection. The first row is the first entered interval when expanded. When collapsed, that same row displays the member's geometric full length and `***` for spring values; deleting it removes only that member's rows. File loading and calculation request creation reject invalid interval groups; the editor permits intermediate values while a user finishes entering a group.

The earlier `GroupDataModel` implementation was the wrong Spread feature. Spread 15.4 row outlines use `SheetView.AddRangeGroup` and cannot coexist with `GroupDataModel`. The editor binds all canonical rows in display order, keeps entered intervals tied to their source rows, and rebuilds outlines when membership or row count changes. Automated tests cover fixed capacity, a singleton without an outline, distant same-member rows, collapse/expand of the first row, detail edits, row insertion/deletion, and selection after expansion.

If explicit lengths total less than the member length with no final blank row, the trailing interval has no spring (confirmed by the user). Rows with an explicit length and zero coefficients represent an un-sprung interval and must survive every projection. ### Risks & Considerations
- Spread row outlines require contiguous displayed detail rows. The editor sorts the filled rows by member, keeps the remaining rows visible through the fixed 100,000-row capacity, and preserves canonical `row` IDs for calculation, persistence, and selection.
- Grouped display indices differ from source `row` indices. Insertion, deletion, auto-move, selection, save order, and 3D highlighting must use stable source identities and only publish a completed atomic change.
- The desktop 3D view currently draws each spring row over the full original member. Partial intervals require span-aware anchors and pick positions; very short spans must be checked against the repeated-glyph spacing and scaling so the drawing does not extend into an unsprung gap.
- An all-zero explicit interval is structural input because it advances the I-end cursor. The current C# projector drops it; losing that row silently shifts every later spring interval.
- Different spring selectors can produce different split points. A union of boundaries is required for multi-case result topology, but selected stiffness must remain case-specific.
- Literal splitting in C# before the Python call would duplicate the existing Python geometry transformation and require remapping loads, joints, rigid zones, notice points, and result IDs. This plan splits before FEM assembly in Python's legacy preparation phase; the solver receives split elements.
- PDF input tables and PDF load diagrams are distinct output paths. `FramePrintPDF/PDF_Manager/PrintInput.cs`, `PdfDocument.cs`, `PDF_Manager.csproj`, and new direct-print files, plus current viewport work, already have unrelated uncommitted edits and must be preserved.
