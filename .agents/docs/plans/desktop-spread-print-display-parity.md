## Implementation Plan: Desktop Spread and PDF Numeric Display Parity

### Purpose
Make existing numeric cells in the WinForms input and result screens use the same precision, exponential notation, rounding, and decimal separator as their corresponding `FramePrintPDF` rows. This is format parity on the same numeric value, not a change to existing screen/PDF unit conversions; numeric source values and saved/calculated data remain intact.

### Scope
- New files: focused `FramePrintPDF/PDF_Manager.Tests/PrintNumericFormatOracleTests.cs` and `FrameWebforCS/tests/SpreadPrintNumericFormatTests.cs` (split the latter into input/result files only if existing STA fixtures require it). The PDF test project already has `InternalsVisibleTo` access to `printManager` and table builders; the desktop test project uses pinned expected strings from those PDF checks, without a new product dependency.
- Modified input files: `FrameWebforCS/components/input/InputMembersComponent.cs`, `InputFixMemberComponent.cs`, `InputLoadComponent.cs`, `InputNoticePointsComponent.cs`, `InputCombineComponent.cs`, and `InputElementsComponent.cs` for the 3D value-dependent `>= 999` print rule. `InputNodesComponent.cs` is an F3 baseline to verify; `InputFixNodeComponent.cs`, `InputJointComponent.cs`, and `InputPanelComponent.cs` need no planned format change because their PDF counterparts use default formatting.
- Modified result files: `FrameWebforCS/calculation/CalculationResultTableWriter.cs` for the canonical base-table path and `FrameWebforCS/components/result/CalculationDerivedViewRenderer.cs` for COMBINE/PICKUP's existing invariant/pre-rounded text; the nine files `FrameWebforCS/components/result/{ResultDisg,ResultReac,ResultFsec,ResultCombineDisg,ResultCombineReac,ResultCombineFsec,ResultPickupDisg,ResultPickupReac,ResultPickupFsec}Component.cs` and their existing formatter/aggregator helpers where parity tests expose a numeric-text difference.
- Modified existing tests: `FrameWebforCS/tests/ResultCombineFsecCtParityTests.cs` and any directly affected result-format assertions only when the approved PDF display contract replaces an older JavaScript rounding expectation; retain separate tests of aggregate numbers, source IDs, and tie selection.
- Dependencies and reference behavior: `FramePrintPDF/PDF_Manager/Printing/PrintInput/*.cs`, `PrintResult/*.cs`, and `Printing/Comon/printManager.cs:58-78`; Spread 15.4 cell types; existing binding, dimension-refresh, and result-presentation code. `printManager.toString` uses `F{n}`/`E{n}` after parsing and uses current culture. The three PICKUP report classes inherit COMBINE result formatting.
- Numeric crosswalk: node coordinates F3; member Cg F3; rigid I/J length F2; spring length/Tx F3, Ty/Tz E2, Tr F2; load L1/L2 F3 and P1/P2 F2; notice positions F3; COMBINE factors F2; element E/G/Xp E2, area F4, torsion/inertia F6 (3D PDF uses default formatting for the latter values at `>= 999`). Displacement F4, reaction F2, and section station F3 with force/moment F2 across base, COMBINE, and PICKUP result rows.
- Exclusions: headings, unit labels, column arrangement, currently blank computed-length columns, print implementation, persistence/calculation values, unrelated Headless changes, and modal/moving-envelope numeric fields with no corresponding PDF formatter. `InputLoadComponent.LL_pitch` remains unchanged: its apparent PDF counterpart is `InputLoadName.rate`, and the current print projection does not establish a field mapping. Default-formatted IDs, flags, and nodal loads remain default.

### Implementation Steps

Implement the print-backed value families in the order below, using the same display oracle for input and result views.

#### Step 1: Establish a print-derived numeric oracle and screen inventory
- [ ] Record each existing screen numeric column, its PDF source field, format, conversion, and applicable 2D/3D branch; mark already-matching and no-counterpart columns explicitly, including `LL_pitch` versus PDF `rate`. Use the audited source locations rather than a global `DecimalPlaces` rule. The PDF is authoritative for numeric format, while existing screen-side unit conversion stays authoritative for the value being formatted.
- [ ] Use `PDF_Manager.Tests` access to internal `printManager` and the existing PDF entry/test seams to pin representative PDF numeric strings, then assert those strings against actual STA Spread `Cell.Text` on the same numeric value. Cover positive, negative, zero, negative zero, null, small `E2` values, F2/F3/F4/F6 midpoint and near-midpoint values, the 3D element `< 999` boundary, and current-culture decimal separators (for example `ja-JP` and a comma-decimal culture). Set and restore culture inside each STA test, serialize tests that touch global culture or existing singleton services, and separately assert committed bound values and existing unit scaling.
- [ ] Characterize L1 and L2 as separate PDF paths from saved strings through the actual table: the printer keeps L1 as text but passes L2 through `parseDouble`. Test decimal text, empty text, and invalid text under dot-decimal and comma-decimal cultures, and distinguish formatting from parse failures. If the existing PDF parser reinterprets invariant text (for example `"1.25"` as `125`), record this as a value-parsing exception to format parity; do not reproduce the misparse in Spread or change the stored/calculated value in this task.
- [ ] For bound `float?` material/input fields, compare the desktop cell's actual value to the value after saved JSON and PDF's `double` parse before comparing format strings. Pin expected text from that actual converted numeric value and explicitly distinguish float-to-double representation from a formatting defect, including the 3D element default-format branch.
- [ ] Exercise the actual JSON load/presentation path for missing result components and empty input cells. `null` is absence rather than a numeric value: preserve each screen's existing blank/zero convention and record its difference from the PDF's missing-to-blank behavior instead of changing result meaning in a numeric-format task.
- [ ] Probe whether Spread 15.4 supports value-dependent 3D element formatting without eagerly styling all 100,000 rows, and whether numeric cell types preserve spring outline `***` and string-backed load lengths.
**Verification**: The PDF oracle and Spread baseline identify specific mismatches, including negative-zero text, without assuming internal PDF helpers are callable from the desktop test assembly. The probe must confirm value-preserving edits, PDF-equivalent rounding, and low-allocation formatting; if any fails, reconsider the cell/formatter approach before changing product code.

### Risks & Considerations
- `NumberCellType.DecimalPlaces` does not express exponential notation. Use Spread 15.4's verified `GeneralCellType.FormatString = "E2"` where the PDF uses E2; verify parsing/editing separately from displayed text.
- PDF `F{n}` uses `double.ToString` while some desktop result paths pre-round with `Math.Floor(value * scale + 0.5)` or emulate JavaScript `toFixed`. Matching digit counts alone can leave different negative and midpoint strings. Compare against independent print-derived cases and change only presentation formatting.
- `InputElementsComponent` is already modified by the preceding approved request. Preserve that diff and add only the 3D conditional rule. The four dirty `FrameWebforCS/Headless/*` paths belong to other work.
- Spread sheets have up to 100,000 rows. A conditional rule must not allocate per-row styles or scan all rows on every refresh; test refresh and scroll behavior on realistic sheet sizes.
- Fixed widths may clip added decimals or E2 text despite correct `Cell.Text`. Visual checks must confirm legibility; small numeric-column width changes are permitted where needed, while table structure remains fixed.
- Existing spring outline summaries and load-length cells can hold nonnumeric text. A numeric cell type or parser applied across a whole column may erase markers or reject valid text.
- L1/L2 are saved strings parsed with `InvariantCulture` for calculation display/request creation. A culture-dependent presentation layer must not rewrite those strings or silently change the current invalid-string-to-zero behavior during this formatting task.
- The PDF's current-culture reparse of saved string-backed L1/L2 can change their *numeric meaning* under a comma-decimal culture. This is outside numeric-format-only scope: reproduce and record the PDF behavior, preserve desktop calculation semantics, and do not claim exact table-number parity for those strings in that culture.
- An existing section-force test pins JavaScript-style midpoint text (`7.625 → 7.63`), which can conflict with the PDF's .NET F2 text (`7.62`). Such a display-contract update must be explicit in the test diff; do not weaken tests of source/aggregate numeric values.
- Some COMBINE section-force inputs are rounded before aggregation. Compare print-format behavior on the existing post-aggregation number rather than expecting a formatting change to recover source precision.
- PDF formatting follows `CurrentCulture`, while some current desktop result strings use `InvariantCulture`; corresponding screen cells should follow the PDF's current-culture decimal separator. Tests must pin representative cultures, compare format on the same numeric value, and verify stored `float?`/result values independently of display strings.
- The current screen multiplies some displacement values by 1000 before display while the PDF projection can print the raw value. Numeric format parity does not remove that existing value/unit conversion. Acceptance must distinguish format from end-to-end table-number equality.
- Some canonical modal/moving and blank computed-length columns lack a PDF counterpart. Their existing display remains as is under the numeric-format-only scope.
- Missing/null inputs and result components are not numeric formatting cases. The desktop's existing blank/zero behavior can differ from the PDF's NaN-to-blank path and must remain unchanged; tests through actual JSON loading must catch accidental changes to that behavior.
