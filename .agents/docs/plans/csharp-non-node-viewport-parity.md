## Implementation Plan: C# Non-Node Viewport Parity

### Purpose
Port the legacy `FrameWebforJS` non-node viewport behavior to the existing `FrameWebforCS` scene, coordinating members, panels, restraints, loads, and analysis results with input edits, node-dependent invalidation, file replacement, mode and page changes, selection, and disposal. Keep a source-level crosswalk and state any unavoidable differences or unfinished behavior.

### Scope
- New files: entity-owned services under `FrameWebforCS/three/` for members, panels, constraints/rigid/notice overlays, loads, and results; focused `FrameWebforCS.Tests/` tests; a C# panel input model/service if absent; this plan.
- Modified files: `FrameWebforCS/three/ThreeService.cs`, `ThreeComponent.cs`, and `SceneService.cs` only as needed for orchestration/selection/render ownership; relevant `FrameWebforCS/components/input/*Service.cs` and `InputPanelComponent.cs` for snapshots/edit notifications; `FrameWebforCS/providers/InputDataService.cs` for panel persistence and committed replacement; relevant result services and routing/sidebar only if required for page and panel modes.
- Dependencies: reuse existing THREE/THREE.OpenGL, WinForms `GLControl`, input JSON, and result services; no second renderer or camera, no dependency upgrade, no change to `FramePrintPDF/` typed viewport.
- Legacy references: `FrameWebforJS/src/app/components/three/three.service.ts:44-215,243-690`; `geometry/three-members.service.ts`, `three-panel.service.ts`, `three-fix-node.service.ts`, `three-fix-member.service.ts`, `three-joint.service.ts`, `three-rigid-zone.service.ts`, `three-notice-points.service.ts`, `three-load/three-load.service.ts`, `three-displacement.service.ts`, `three-react.service.ts`, and `three-section-force.service.ts`.
- Ownership: lead owns shared coordinator, GL component, provider, routing, and plan. Workers own disjoint entity service and test files; panel input files stay with the panel worker. Unrelated `FrameWeb.sln` and `tools/PythonNetDebugProbe/**` changes belong to the user and must remain untouched.

### Risks & Considerations
- Panel input and `shell` JSON roundtrip now exist; preserve partially entered rows independently of drawable three/four-node geometry. C# rejects invalid or duplicate node IDs that the JS parser could retain.
- `InputDataService.JsonDataOpen` parses before apply and defers `Changed`/`FileReplaced` observers until all sections are installed. Parse/camera/observer failures have regression coverage; unexpected failures inside service mutation are not rollback-safe.
- Restraint, rigid and notice services now publish viewport edit events and the coordinator subscribes to them. Keep updates event-driven rather than scanning 100,000 blank rows per frame.
- `InputLoadService.SelectCase` raises `SelectedCaseChanged`, distinct from `CasesChanged` for edits to the case list. JS uses distinct display projections for support, joint and load values, unlike C# save JSON.
- Old JS `three.service.ts:97-149` does not update panel/constraint/result shapes for every node edit; this task requires stronger dependency invalidation. Document that difference near implementation.
- Old JS load `detectObject` immediately returns; old panel sparse-node check is wrong; `three.component.ts:97` has no cleanup. Corrected C# behavior requires explicit crosswalk comments, not an unqualified parity claim.
- Native OpenGL appearance and close/reopen were not verified in the node slice. Headless scene tests cannot establish visual parity.
- Run .NET gates sequentially; the previous node work saw locked default test output and used a repository-local ignored `obj` output path as a fallback.

### Open Questions
- None blocking from the user request. Implement legacy mode-specific GUI controls and grid selection where behavior exists; name any unimplemented control and reason explicitly in the final inventory.
